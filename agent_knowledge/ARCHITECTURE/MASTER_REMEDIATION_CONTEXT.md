# Master Remediation Context

This document is the single source of truth for all future implementation work on the LegalDoc Automator. It consolidates the findings from previous audits that survived the architectural decision process. Do not reintroduce rejected recommendations.

---

## 1. Executive Summary

This architecture context guides the transition of the LegalDoc Automator from a rapid-prototype implementation to a maintainable, generalized system.
*   **Architectural Findings:** The system currently relies on heavily mixed data, business logic, and presentation layers. Templates strictly own presentation logic, while code strictly owns business logic (extraction, validation, chronology).
*   **Technical Debt:** The repository contains numerous temporary scripts, one-off healers, and generated artifacts that obscure the core functionality. Hardcoded case-specific rules represent true debt, while many string replacements are legitimate normalization rules.
*   **SD-Specific Findings:** The current title-chain engine is heavily tailored to Sale Deeds, forcibly collapsing nuanced events into a generic `"TRANSFER"` bucket and relying on textual substitution rather than an entity graph.
*   **Future Scalability:** Supporting complex document types (Gifts, Wills, Partitions) requires preserving semantic event types and relational metadata, rather than an immediate architectural rewrite.

---

## 2. Accepted Findings

The following findings have been explicitly approved for remediation:

*   **Case-Specific Hardcodes:** Case-specific overfitting strings and logic (e.g., hardcoded names, addresses, plot numbers) exist and must be removed.
*   **Technical Debt Clutter:** Root directory clutter (diffs, `.docx` outputs) and one-off case healing scripts (`heal_session_*.py`, `reorder_chain.py`) are confirmed technical debt.
*   **Field Naming Inconsistency:** Alias proliferation (e.g., `title_chain` vs `chain`, `adr` vs `address`) and `CHAIN_SCHEMA.md` documentation mismatches are valid architectural debt.
*   **Fragmented Padding/Healing:** Logic to pad arrays or heal data is fragmented across `app.py`, `extractor.py`, and `processor.py`.
*   **Text Replacement Necessity:** Not all string replacements are bad. DevLys normalization, extraction compensation, and template compensation exist and require individual evaluation.
*   **Event-Type Collapse:** The current system forcibly maps distinct legal events (e.g., Wills, Gifts) into a generic `"TRANSFER"` type, which breaks future scalability.
*   **Tool Organization:** Useful infrastructure (e.g., parity audits, E2E tests) needs clear separation from temporary investigation scripts.

---

## 3. Rejected Findings

The following recommendations were explicitly evaluated and rejected. Do not attempt to implement them:

*   **LLM-Generated Legal Narratives:** Rejected. Final Hindi legal text must remain deterministic and strictly controlled via templates and Python logic, not natively generated by the LLM.
*   **Immediate Ownership Graph Rewrite:** Rejected. The current linear title-chain array works sufficiently for Sale Deeds. A ground-up rewrite or complex recursive narrative engine is unnecessary risk.
*   **Rewrite Rendering Pipeline (Processors):** Rejected. There is insufficient evidence to justify replacing or fully unifying `RMTemplateProcessor` and `SDTemplateProcessor` or removing all string replacement rules.
*   **DevLys Converter Rewrite:** Rejected. The current legacy font conversion engine remains functional.
*   **Flattening All Nested Objects:** Rejected. Removing logical groupings (e.g., `sale.amount`) solely for naming consistency is discouraged.
*   **Delete Everything That Looks Temporary:** Rejected. Age does not equal uselessness. Valuable historical investigation scripts must be archived, not blindly deleted.

---

## 4. On-Hold Findings

The following items represent potential long-term goals but require further architectural review and are currently on hold:

*   **Ownership Graph & State Machine:** Building an adjacency-list graph data structure or a Python engine validating fractional mathematical splits over time.
    *   *Evidence Required:* Proof that current linear arrays fail to model required complexity for new deed types *and* that a purely flat extraction mapping is no longer feasible.
*   **`title_engine` Module:** Creating a generic, isolated module separate from specific deed implementations.
    *   *Evidence Required:* Introduction of 3+ completely distinct document categories (beyond SD and RM) demonstrating sufficient shared pipeline needs to justify breaking isolation.
*   **BaseExtractor / BaseProcessor Unification:** Unifying RM and SD logic under shared bases is deferred to maintain strict RM/SD isolation.
    *   *Evidence Required:* Overwhelming duplication metrics that demonstrably slow down development across both RM and SD, proving isolation is worse than coupling.
*   **Template Compensation Removal:** Modifying underlying `.docx` templates to remove string matches (e.g., surgical `è` ligatures) requires synchronized, meticulous review to prevent parity regressions.
    *   *Evidence Required:* A formalized process and verified tools to guarantee Word XML modifications do not break downstream document formatting or cause regressions.
*   **Full App Modularization:** Breaking down the monolithic `app.py` into smaller Flask Blueprints.
    *   *Evidence Required:* The monolithic file size actively causing merge conflicts, severe routing bugs, or preventing testability of discrete endpoints.
*   **Session Schema Redesign / Field Migration:** A mass renaming of keys across the extractor, session data, and templates requires a dedicated migration strategy.
    *   *Evidence Required:* An approved, robust migration tool capable of safely translating legacy aliases in thousands of `.docx` templates and old JSON session payloads.

## 5. Text Replacement Classification Model

All existing and future string replacements and normalizations must be evaluated against this official classification model:

1.  **CASE_SPECIFIC (Approved for Removal):** Strict overfitting strings (e.g., specific names, lease numbers) used to patch individual cases. Strictly forbidden.
2.  **DEVLYS_NORMALIZATION (Approved to Keep):** Valid adaptations for the legacy DevLys font (e.g., global date hyphen parsing, `ç` -> `iz`, identity boilerplate brackets). May eventually be moved to `devlys_converter.py`.
3.  **EXTRACTION_COMPENSATION (Approved for Future Relocation):** Rules covering AI/OCR weaknesses (e.g., stripping trailing commas from AI output, fixing AI punctuation hallucinations). Should eventually move upstream to the schema or extractor layer.
4.  **TEMPLATE_COMPENSATION (On Hold):** Python string replacements compensating for typos, formatting quirks, or legacy spelling embedded directly in the `.docx` templates (e.g., forcing standard `/k` into surgical `è` ligatures). Changing these requires modifying the actual Word templates.

## 6. Canonical Field Strategy

The project adopts full, readable words over terse aliases while preserving established logical groupings. A mass migration is currently on hold, but this serves as the target standard:

*   **Parties:** `address` (not `adr`), `aadhaar` (not `id`), `age` (not `a`), `caste` (not `c`), `name` (not `n`).
*   **Party Groups:** `sellers` / `buyers` (SD), `borrowers` (RM), `witnesses` (not `ws`).
*   **Property:** `properties` (not `ps`), `land_area`, `const_area`, `area_unit` (not `unit`).
*   **Title Chain:** `title_chain` (not `chain`), `executant_name` (not `executant.name`), `reg_book` (not `book_no`), `reg_vol` (not `volume_no`), `reg_page` (not `page_no`).
*   **Financial/Deed (Nested):** `sale.amount` (not `amount`), `sale.amount_words`, `sale.payment_details`, `deed.execution_date` (not `rd`).

**Migration Guidance:** When implemented, this requires updates to prompts, a backward-compatibility layer in `load_case_session`, processor refactoring, and comprehensive template updates.

## 7. Title Chain Future-Proofing

To support diverse document types (Wills, Gifts, Partitions) over the next 10 years without rewriting the system:

*   **Accepted:** Preserve real event types during extraction (`WILL`, `GIFT_DEED`, etc.) instead of collapsing them into `"TRANSFER"`. Support future deed types by routing them to safe generic textual templates initially. Add passive metadata like `consideration_type`.
*   **Partially Accepted:** Lineage tracking (`event_id`, `parent_event_ids`) and ownership shares are accepted as passive data points for extraction, but using them for active programmatic math or graph traversal is delayed.
*   **Rejected:** LLM-generated full narratives.
*   **On Hold:** Full programmatic ownership graph and recursive narrative engines.

## 8. Technical Debt Prioritization

Debt should be addressed in the following order:

### Safe To Execute (High Confidence / Low Risk)
*   Delete root directory clutter (diffs, logs, generated DOCX).
*   Delete hardcoded case healers (`heal_session*.py`) and overfitted logic scripts (`reorder_chain.py`).
*   Archive one-off investigations (`check_ligature.py`, `dump_tags.py`) into dedicated folders.
*   Relocate valuable tools (`audit_parity.py`, `test_e2e_sd.py`) to `tools/` and `tests/`.

### Medium Risk (Needs Validation)
*   Relocating `EXTRACTION_COMPENSATION` rules from the rendering layer to the schema validation or extractor layer.
*   Reviewing `debug_gen.py` to determine if it should be archived or converted into a CLI tool.
*   Adding lineage metadata fields (`parent_event_ids`) to extraction prompts (requires prompt stability testing).

### High Risk (Requires Architectural Review)
*   Removing `TEMPLATE_COMPENSATION` rules (requires synchronized Word template updates).
*   Relocating `DEVLYS_NORMALIZATION` rules into the core DevLys converter.
*   Executing the Canonical Field Migration.

## 10. Guardrails

The following project constitution acts as the ruleset for all future agents and implementation work:

1.  **No Case-Specific Logic:** Hardcoded patches for specific parties, properties, or edge-case documents are strictly forbidden.
2.  **RM/SD Isolation:** Registered Mortgage (`modules/rm`) and Sale Deed (`modules/sd`) must not cross-import. Unification is paused.
3.  **Root-Cause-First Fixes:** Always attempt fixes in order: 1. Extraction, 2. Schema/Validation, 3. Business Logic, 4. Templates, 5. Rendering (Post-Processing last).
4.  **Deterministic Drafting:** Final legal wording comes from template selection and field population, never direct LLM generation. Templates strictly own presentation logic.
5.  **Evidence-Before-Claims:** Identify the exact layer of a problem (data, logic, template) and provide source evidence before proposing architectural fixes.
6.  **Multi-Case Validation:** Generic codebase fixes must be validated against multiple representative cases (at least 3 from `cases/`) to ensure backwards compatibility and prevent logic reduction.
