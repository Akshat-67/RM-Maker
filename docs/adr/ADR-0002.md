# ADR-0002: DevLys Rendering Boundary

## Status
Accepted

## Date
19-07-2026

## Context
Standard `.docx` templates for legal deeds contain legacy styling where the default run font is set to `DevLys 010` or `Kruti Dev 010`. To compile these templates correctly, the text strings injected into the templates must be mapped to the corresponding legacy ASCII-font representation. 
If conversion is performed too early, it corrupts data formats. If it is performed too late or incompletely, it causes text rendering anomalies (e.g. text blocks showing up as fallback Times New Roman or showing garbled text).

## Decision
Legacy font translation (`Unicode_to_KrutiDev` / `Unicode_to_DevLys`) must occur **strictly at the rendering boundary** inside the template processor, immediately before passing the context variables to `docxtpl`.
- Domain extractors and schema managers must operate exclusively on Unicode (see [ADR-0001](file:///c:/Users/aksha/Documents/RM%20Generator/RM-Maker/RM-Maker-MAIN/docs/adr/ADR-0001.md)).
- The template processors (`RMTemplateProcessor` and `SDTemplateProcessor`) take a clean Unicode dictionary, clone it, traverse the string values, translate them to DevLys, and feed the translated context directly into `docxtpl.render()`.
- The source templates themselves remain the compatibility layer; they dictate which runs require legacy mapping via their styled font properties.

## Alternatives Considered
- **Converting during Extraction**: Rejected. Ingestion pipelines and AI extractors would have to translate Gemini's Unicode responses into legacy encodings before saving. This would corrupt `session.json` and break database integrity.
- **Client-Side DevLys Conversion on Save**: Rejected. Converting to DevLys in browser forms would result in users editing unreadable characters in text fields, breaking the UI workspace.

## Consequences
- **Positive**: Complete separation of concerns. Data storage, extraction, and validation rules remain clean, while the rendering engine isolates formatting quirks.
- **Negative/Neutral**: String-traversal converters add a small rendering CPU overhead. To mitigate this, conversion checks must use optimized compiled regular expressions (`[\u0900-\u097F]`) to match and translate only active Devanagari blocks.

## Future Considerations
Isolating conversion to the rendering boundary ensures that if a new output format (such as PDF or standard HTML) is introduced, we only need to write a formatter for that specific boundary.
