# ADR-0003: RM and SD Independent Pipelines

## Status
Accepted

## Date
19-07-2026

## Context
RM-Maker supports two main document workflows: Registered Mortgage (RM) and Sale Deed (SD). Early implementations attempted to merge these pipelines into a single monolithic schema and UI workflow. However, RM and SD serve different financial operations and use completely different data sets:
- **RM**: Focuses on financing, loan amounts, interest rates, property values, bank officer roles, and schedules.
- **SD**: Focuses on property sales, transaction values, historical title deed sequences, seller/buyer dynamics, and chronological narrative histories.
Forcing them into a single schema created fragile code, where modifying an SD feature would break the stable RM compiler.

## Decision
The RM and SD modules must operate as **independent pipelines** from end to end, sharing only common utility code.
- **Independent Folders**: All domain-specific logic resides in separate directories: `modules/rm/` for Registered Mortgage and `modules/sd/` for Sale Deed.
- **Independent Schemas**: Schemas remain isolated (`RM_SCHEMA.md` and `SD_SCHEMA.md`).
- **Independent Processors**: Separate compilation handlers (`RMTemplateProcessor` and `SDTemplateProcessor`) ensure that updates to one pipeline cannot introduce regression issues in the other.
- **Shared Infrastructure**: Share only generic, low-level modules (e.g. image rotation, PDF extraction, file storage API endpoints, and raw AI wrappers).

## Alternatives Considered
- **Unified Pipeline Model**: Rejected. A single schema would lead to hundreds of unused optional fields and high complexity in form handling.
- **Microservices Separation**: Rejected. Splitting the app into completely separate microservices would complicate local deployment, increase infrastructure costs, and double the overhead of e-Panjiyan extensions.

## Consequences
- **Positive**: High pipeline stability. Changes in the newer Sale Deed features can be deployed rapidly without risking regressions in the production-hardened RM module.
- **Negative/Neutral**: Requires maintaining separate template files and schemas in parallel, resulting in slight duplication of boilerplate code.

## Future Considerations
This design permits the introduction of additional legal pipelines (such as Lease Deeds or Power of Attorney documents) by simply dropping a new domain module under `/modules/` without impacting existing flows.
