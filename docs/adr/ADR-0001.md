# ADR-0001: Unicode as Canonical Representation

## Status
Accepted

## Date
19-07-2026

## Context
RM-Maker processes documents containing both English and Devanagari (Hindi) text. Historically, legal document compilers often forced legacy font encodings (such as DevLys 010 or Kruti Dev 010) throughout the entire pipeline. However, these legacy encodings map Hindi characters onto standard ASCII codes (e.g. typing "f" outputs a Hindi character in MS Word). This causes major issues:
1. Standard text fields cannot be read by standard search or regex engines.
2. Web UI inputs and textareas display unreadable gibberish unless specific, obsolete fonts are loaded in the browser.
3. Natural Language Processing (NLP) models (like Gemini) fail completely when extracting to or from ASCII-mapped legacy text.

## Decision
All internal data structures, API endpoints, schema validations, user interfaces, and database entries must use standard **Unicode Devanagari** encoding. 
- Input fields on case dashboard screens must display Hindi in clean, standard browser Unicode fonts (e.g. `Segoe UI`, `Mangal`).
- Transliterator calls and local `Sanscript` helpers convert English to Devanagari Unicode.
- Legacy encoding (DevLys) is strictly isolated and applied only at the rendering boundaries (see [ADR-0002](file:///c:/Users/aksha/Documents/RM%20Generator/RM-Maker/RM-Maker-MAIN/docs/adr/ADR-0002.md)).

## Alternatives Considered
- **Universal DevLys Storage**: Rejected. Storing legacy ASCII text internally would break AI extraction, rule validations, and require custom font overrides in browser workspaces.
- **Bilingual Unicode/DevLys Schemas**: Rejected. Storing two versions of every Hindi string (e.g. `borrower_name` and `borrower_name_devlys`) introduces significant database schema bloat and maintenance overhead.

## Consequences
- **Positive**: Text fields remain fully searchable, readable, and editable by both users and LLMs. Regular expressions (such as boundary name check helpers) work out-of-the-box.
- **Negative/Neutral**: Requires a reliable, performance-optimized conversion helper to translate Unicode to DevLys when rendering the final `.docx` templates.

## Future Considerations
If target registration portals phase out legacy encodings and accept Unicode text files natively, the DevLys translation layer can be toggled off at the rendering boundary without changing the core application logic.
